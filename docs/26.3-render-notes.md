# 26.3: how the renderer hooks in, and what Iris does there

Notes taken while porting the GPU foliage renderer to 26.3 (September 2026), kept so none of it has to be dug
out twice. Everything here was read from the 26.3 client or from Iris 1.11.6 and Sodium 0.9.2 for 26.3, not
guessed.

## What 26.3 changed

- The render API moved from `com.mojang.blaze3d.*` to `com.mojang.renderpearl.*` (`api`, `backend`, `frontend`).
  `RenderSystem`, `PoseStack`, `Std140Builder` and the buffer builders stayed in blaze3d.
- The shading language changed with it: `#include <ns:file.glsl>` in place of `#moj_import`, every input and
  output names its `layout(location = N)`, and the lightmap is read through `sample_lightmap.glsl`. The mod
  therefore carries a set of shaders per generation; only the set a version speaks ships in its jar.
- The whole world is drawn inside **one render pass** the game opens and hands down. No mod may open its own
  inside it, write to a buffer while it is open, or compile a pipeline there.
- A pipeline is no longer handed its program. The game compiles one from the shaders the pipeline names, and
  `PipelineCache.get()` compiles it **the first time it is asked for**. Nothing needs registering anywhere --
  this is what Sodium relies on, and `GlDevice.getOrCompilePipeline`, which the mod used until 26.2, is gone.

## Porting it again, one piece at a time

The first port was reverted, and 26.3 is being brought in again a step at a time, each one tested before the next:
vanilla with the chunk mesh keeping every plant, then the GPU renderer on vanilla (OpenGL and Vulkan), then Sodium,
resource pack core shaders and Iris.

**Step 1 (done):** 26.3 builds and loads. The mod imports the classes that moved from `com.mojang.renderpearl`; the
classes it uses for blocks, models and chunks are unchanged. Iris, Polytone, Sodium's shaders and the terrain shader
splicing are guarded out of 26.3, and the jar carries none of the mod's shaders. The draw hook is not registered, so
the renderer is never started and the chunk mesh keeps the foliage whatever the setting says.

Why the GPU renderer waits: up to 26.2 the chunks' `renderGroup` opened and closed a render pass of its own, so
Fabric's `AFTER_OPAQUE_TERRAIN` arrived with no pass open and the mod opened its own. In 26.3 `addMainPass` opens one
pass ("Main", or "Solid" with improved transparency) around the whole opaque terrain and features, and Fabric fires the
event from inside it (it wraps `renderGroup` in `executeSolid`). With a pass open, `FrontendCommandEncoder` refuses a
new pass, `writeToBuffer`, copies and clears (`IllegalStateException`); mapped writes, which `DynamicGpuData` uses,
are still allowed.

**Step 2 (done):** the GPU renderer on vanilla, tested on OpenGL and Vulkan, switching between CPU and GPU, reloading
the shaders and with improved transparency on and off. `END_EXTRACTION` prepares (`GpuFoliageRenderer.draw` →
`submitDraws`, which writes everything and leaves a pending draw), `LevelPassMixin` draws into vanilla's pass. The
shaders are `core/foliage_modern.vsh`/`.fsh`, vanilla's 26.3 block shaders with the sway, and only the 26.3 jar
carries them. Every optimization of the older versions is shared code and applies unchanged: packed per-vertex values,
regions drawn in runs, whole regions skipping the per-section frustum test, all transforms in one mapping, the
rebuild budget and the adaptive radius. What 26.2 draws with that 26.3 does not yet is the terrain's own shaders
(resource pack core shaders); that is a later step.

### Step 2 research: the GPU renderer on vanilla

Read from the 26.3 client, 27 September 2026.

- **When to prepare.** `Minecraft.renderFrame` runs `GameRenderer.extract` and then `GameRenderer.render` every frame,
  and `DynamicGpuData.reset()` only at the end of it. Fabric's `LevelExtractionEvents.END_EXTRACTION` fires at
  `LevelExtractor.extract` RETURN: the camera state (position, cull frustum, `viewRotationMatrix`) is filled in, no
  render pass is open, and marking sections dirty there is what `LevelExtractor` itself does. Everything that writes
  -- region buffers, the sway settings, the interaction buffer, the transforms, the pipeline compile -- belongs there.
- **Where to draw.** Inside vanilla's pass, which only a mixin hands out: `LevelRenderer.executeSolid(chunks,
  featureFrame, renderPass)`, just before `featureFrame.executeSolid(renderPass)` -- after the opaque terrain, before
  the solid features, the moment `AFTER_OPAQUE_TERRAIN` marks. Fabric injects after that same call, so the two do not
  collide.
- **The model view.** At that point in the frame the model view stack has not had the camera rotation pushed yet, so
  the matrix is `cameraRenderState.viewRotationMatrix` -- the one vanilla pushes and draws its terrain with.
- **The index buffer.** The shared sequential buffer is replaced, the old one closed, whenever it has to grow. Vanilla
  now asks for a size while preparing (`requestIndexCount`), grows every shared buffer once in `prepareTranslucents`,
  before its pass opens, and reads it inside with `getBuffer()`. Growing it from inside the pass would close the buffer
  the terrain was just drawn with.
- **Draw rules.** A pipeline's colour targets must match the pass's (`ColorTargetState.DEFAULT`, as vanilla's terrain
  in the same pass); every uniform a pipeline declares must be set on the pass or the draw throws `Missing uniform`;
  uniforms set on a pass stay set for what is drawn after. `bindDefaultUniforms` sets `Projection`, `Fog`, `Globals`
  and `Lighting`.
- **Compiling.** `RenderSystem.getCompiledPipelineNullable` compiles on first request, in the current `PipelineCache`,
  and does not remember a failure, so a pipeline that does not compile would be compiled again on every request. A
  resource reload replaces the cache and closes every pipeline in the old one, the mod's included.
- **Shaders.** Same uniform blocks and names as 26.2 (`Globals`, `DynamicTransforms`, `Projection`, `Fog`,
  `sample_lightmap`), but `#include <ns:file.glsl>` instead of `#moj_import`, the
  `GL_ARB_separate_shader_objects` extension, and a `layout(location = N)` on every input and output. Includes live
  in `shaders/include/*.glsl`. Every shader is compiled to SPIR-V and checked: each vertex input must match a vertex
  format element by name and type, vertex outputs must match fragment inputs by location, and every uniform must be in
  the pipeline's bind groups.
- **Unchanged:** `VertexFormat.builder`, `DynamicGpuData.Transform` (was `DynamicUniforms.Transform`),
  `RenderPass.drawIndexed`, `AbstractTexture.getSampler()`, `GameRenderer.lightmap()`.

### Step 3 research: Sodium 0.9.2

Read from Sodium 0.9.2+mc26.3, 27 September 2026.

- **What the mod reaches is unchanged from 26.2.** `SodiumWorldRenderer.instanceNullable()`, `isBoxVisible(6 doubles)`,
  `scheduleRebuildForChunk(x, y, z, boolean)`, `RenderRegionManager.uploadResults(Collection, UniformBufferManager)`
  (SodiumMeshSwapMixin's >=26.2 target), `BuilderTaskOutput.section`, `RenderSection.getChunkX/Y/Z`,
  `ChunkBuildOutput` and `world.LevelSlice` all exist with the same signatures.
- **Occlusion is current when the foliage is prepared.** Sodium runs `setupTerrain` -- its visibility graph, chunk
  updates and uploads -- from `LevelExtractor.extract`, at `consumeFrustumUpdate`, before Fabric's `END_EXTRACTION`
  at its RETURN. So `isBoxVisible` answers for this frame, as it did in 26.2 when the foliage was prepared later.
  Sodium overwrites `LevelExtractor.setSectionDirty` to schedule its own rebuild, which the mod also asks for directly.
- **Sodium draws in the same pass.** It replaces the `ChunkSectionsToRender` vanilla prepares (wrapping
  `prepareChunkRenders`) and draws its opaque and cutout layers from `renderGroup`, inside vanilla's pass; it does not
  touch `executeSolid`, so LevelPassMixin still draws the foliage right after them. Its pipelines use push constants;
  the mod's declares none, and sets every uniform it declares itself.
- **The split still holds.** With Fabric's renderer API loaded Sodium meshes every block model through
  `FRAPIEmitter` -> `emitQuads(..., LevelSlice, ...)`, where `GpuFoliageModel` withholds the foliage.
- **Not carried over yet:** drawing the foliage with Sodium's own chunk shaders (`SodiumFoliageShader`, which reads
  their source and compiles them with the mod's vertices), so it is lit and fogged exactly as Sodium's terrain. On 26.3
  the foliage is drawn with the mod's own pipeline while Sodium draws the chunks.

**Step 3a (done):** Sodium with the GPU foliage, tested on OpenGL and Vulkan. No code was needed: everything the mod
reaches in Sodium was already shared code, and what had kept it from working were the dev run's JVM arguments and
drawing into vanilla's pass.

### Step 3b research: drawing the foliage with Sodium's shaders

On 26.2 `SodiumFoliageShader` reads Sodium's cutout chunk shaders (or a resource pack's in their place) from the
resource manager, replaces the include that decodes Sodium's vertices with one reading the mod's, points Sodium's
uniforms at vanilla's blocks, and compiles the result as the mod's `SODIUM_PIPELINE`. On 26.3:

- **Sodium's shaders** (`sodium:shaders/blocks/block_layer_opaque.vsh`/`.fsh`, includes under
  `sodium:shaders/include/`) changed only in language: `#include` for `#moj_import`, a location on every input and
  output, the fragment shader at `#version 460`, and OIT variants the mod does not use (`#include <minecraft:oit.glsl>`
  declares nothing without `OIT`). `chunk_vertex.glsl` still fills `_vert_position`, `_vert_color`,
  `_vert_tex_diffuse_coord(_bias)`, `_vert_tex_light_coord`, `_draw_id` and `_material_params` in `_vert_init()`;
  `globals.glsl` (`u_Globals`), `fog.glsl` and `chunk_material.glsl` are unchanged.
- **Push constants every time.** 26.3 compiles every shader for Vulkan, so `VULKAN` is always defined and Sodium's
  region offset, time and region id are always in a push constant block -- the textual `#else` branch still declares
  them loose, which is what the mod's rewriting keys on, and it already drops the block.
- **Sodium's pipeline** (`ShaderChunkRenderer.createShader`): its two bind groups, 20 bytes of push constants, cull on,
  `USE_VERTEX_COMPRESSION`, `USE_FOG`, `ALPHA_CUTOUT 0.5` for cutout.
- **Vanilla's blocks were reordered.** `DynamicTransforms` is now `ModelViewMat, TextureMat, ColorModulator,
  ModelOffset` and `Globals` is `CameraBlockPos, GlintAlpha, CameraOffset, GameTime, ScreenSize, MenuBlurRadius,
  UseRgss`. The mod declares copies of these blocks with renamed members; with 26.2's order they would read the
  region's offset from the wrong bytes, silently.
- **Compiling a rewritten shader.** `ShaderSource` is an interface with `getShader`, `getInclude` and `close` (no longer
  a lambda), `GpuDevice.precompilePipeline` and `ShaderManager.getShader` are gone. A pipeline whose source is built
  by the mod is compiled with `GpuDevice.compilePipeline(pipeline, source, executor).join().finishCompile()`, outside
  the game's `PipelineCache`, so the mod owns it and closes it when the shaders reload. A GLSL error comes back as an
  exception from `join`, not as null.

**Step 3b (done):** the foliage is drawn with a copy of Sodium's chunk shaders while Sodium draws the chunks, tested on
OpenGL and Vulkan. `SodiumFoliageShader` builds the copy as on 26.2 -- with `#include`, 26.3's member order for
`DynamicTransforms` and `Globals`, and a location on every replaced input -- writes every include out itself, and
compiles it with `GpuDevice.compilePipeline` and a `ShaderSource` of its own into a pipeline it closes when the shaders
reload. The foliage's uniform blocks moved into `shaders/include/foliage_uniforms.glsl`, which `foliage_modern.vsh` and
the copy both include; only the 26.3 jar carries it.

### Step 4 research: resource pack core shaders (the terrain's own shaders)

On 26.2, with no Sodium, the foliage is drawn with the terrain shader in use -- vanilla's or a resource pack's
`core/terrain` -- so it is lit and coloured as the chunks: `TerrainFoliageShader` renames every read of `Position`
to a swayed copy, puts the mod's inputs next to `Position`'s declaration and adds a `main` that sways and then runs the
shader's own. The fragment shader is the terrain's as it is. On 26.3:

- **`core/terrain` has two variants.** Without `MULTIDRAW_TERRAIN` it reads the section from the `ChunkSection` block
  (`ivec3 ChunkPosition; float ChunkVisibility`); with it, from vertex attributes at locations 4 and 5 -- the locations
  `foliage_modern` gives `SwayCell` and `SwayWeights`. The mod draws the first variant; a pack's shader may use any
  location for its own inputs, so the spliced inputs should keep clear of the low ones.
- **A new block, `TerrainUniform`** (`mat4 ModelViewMat; ivec2 TextureSize`), carries the view matrix and the atlas size
  that 26.2 packed into each section. `DynamicGpuData.writeTerrainTransform(modelView, width, height)` writes it, in a
  storage of its own. The fragment shader samples through `texture_sampling.glsl` with `1 / TextureSize` and fades a
  section in with `chunkVisibility`, a new vertex output at location 4.
- **The section block must not come from `DynamicGpuData`.** `writeChunkSections` and `writeChunkSectionsInstanced` share
  one storage and replace it whenever the kind asked for changes; vanilla asks for the instanced kind when it draws with
  multidraw, and the buffer it gets is the vertex buffer its chunks are drawn from. Asking for the other kind mid-frame
  closes it -- the "Vertex buffer at slot 1 has been closed" of the first attempt. A section's block holds the region's
  corner and full visibility, which never change for a region, so each region can own one, written once.
- **Pipeline:** as vanilla's terrain snippet, which is private: `GLOBALS`, `FOG`, `SAMPLER0`, `SAMPLER2`, `PROJECTION`,
  `CHUNK_SECTION`, `TERRAIN_INFO`, the block format with the mod's values, quads, default depth and colour target,
  `ALPHA_CUTOUT 0.5`.
- **Compiling** goes as for Sodium's copy (`GpuDevice.compilePipeline` with the mod's `ShaderSource`, closed on reload),
  both shaders read from the resource manager -- the topmost pack's -- with their includes written out.
- **Test packs:** Emissive Trims replaces only `core/entity.fsh`, NotVisuals only post effects, Shadify only models;
  none of them replaces `core/terrain`.

**Step 4 (done):** without Sodium the foliage is drawn with the terrain shaders in use, tested on OpenGL and Vulkan
with a test pack whose `core/terrain.vsh` tints the terrain red -- the GPU foliage turned red with it. The terrain's
vertex shader has its includes written out before it is spliced: the new `main` reads the camera and the time, which
only its includes declare (26.2's shader manager handed shaders over already expanded). The mod's inputs sit at
locations 14 and 15. Each region owns its `ChunkSection` block, made once while a frame is prepared; the view and the
atlas's size go through `writeTerrainTransform`.

### Step 5 research: Iris 1.11.6

Read from Iris 1.11.6+mc26.3 against 1.11.4+mc26.2 (what the mod works with on 26.2), 28 September 2026. Some of
what the first attempt believed (in *Iris 1.11.6 on 26.3* below) turns out to be wrong; this supersedes it.

- **How a pack's program reaches a draw.** `MixinShaderManager_Overrides` wraps `RenderSystem.getCompiledPipelineNullable`:
  for a pipeline in `IrisPipelines`, it takes the pack's program for the mapped `ShaderKey` and builds a
  `FrontendRenderPipeline` around it from the compiled pipeline's own `CreateInfo`, tying every vertex attribute by
  `glGetAttribLocation` of `iris_<name>`, then `<name>`, and keeping the pipeline's uniform list and indices. The
  pipeline has to compile on its own first; its result is what gets wrapped.
- **A public way in.** `IrisApi.assignPipeline(RenderPipeline, IrisProgram)` puts a mod's pipeline in that table
  (`ShaderKey.findBestMatch`: with `ALPHA_CUTOUT` and `IrisProgram.TERRAIN_CUTOUT`, the vanilla-patched
  `TERRAIN_CUTOUT` key, with a warning in the log since the mod's format is not Iris's exactly);
  `assignPipelineShadow` does the same for the shadow pass, and `registerShadowRenderCallback` still exists. With
  Sodium drawing the chunks, the vanilla terrain keys serve only pipelines like `CUTOUT_BLOCK`.
- **Framebuffers.** An Iris program binds the pack's own framebuffer when it is set up (`ExtendedShader.iris$setupState`:
  before or after translucency), from `GlRenderPipeline.bind`; a draw with any other program inside a pass gets the
  vanilla target back (`MixinGlCommandEncoder`). `ImmediateState.safeToMultiply` is never set, so a pass binds its own
  target as usual first.
- **Depth.** Only `UndoReverseZOne`, an empty mixin, is registered; `UndoReverseZThree/Four/Five` are in the jar but not
  applied, and `IrisApi.isReverseZDuringShaders()` is true outside shadows. The main pass keeps vanilla's reversed
  depth, so `DepthStencilState.DEFAULT` is right; in the shadow pass `MixinGlRenderPipeline` flips every comparison.
- **Uniform blocks and samplers are bound at fixed points by name** (`MixinGlProgram.iris$setupBindings`, from the
  pipeline's `CreateInfo` uniform list at every bind): DynamicTransforms/TerrainUniform 0, CloudInfo 1, Projection 2,
  Globals 3, Fog 4, Lighting 5; Sampler0/u_BlockTex 0, Sampler1 1, Sampler2/u_LightTex 2. **Any other name gets no
  binding**: the mod's `FoliageSway` and `FoliageInteraction` would never reach the program as things stand.
- **Unchanged from 26.2** for what the mod calls: `IrisRenderingPipeline.createShader/createShadowShader`,
  `ShaderCreator`, `TransformPatcher`, `IrisVertexFormats`, `BlockSensitiveBufferBuilder`, `WorldRenderingSettings`,
  `ShaderSupplier`.
- **Why the first attempt showed nothing is still not known.** The depth theory it ended on does not hold (see above).
  The rest can only be settled by trying, one piece at a time.

**Step 5a (done):** with a pack loaded the foliage reaches the pack's buffers, lit by the pack, not swaying yet.
The pack pipeline (`foliage_shader_pack`: `foliage_modern` over Iris's terrain format and the mod's two values) is
handed to Iris once with `IrisApi.assignPipeline(..., TERRAIN_CUTOUT)`, compiled while the frame is prepared and asked
for again inside the pass, where Iris gives back the pack's program. Two things turned up while testing:

- **View bobbing.** With a pack loaded Iris takes the bobbing out of the projection and multiplies it into
  `cameraRenderState.viewRotationMatrix` just before `LevelRenderer.render` (`MixinModelViewBobbing`). Foliage drawn
  with the view as it was extracted slid about with every step. Whatever holds the view -- each region's transform, the
  terrain's block -- is now written at `LevelRenderer.render` HEAD (LevelPassMixin), when the view is final and no pass
  is open yet.
- **The gap between preparing and drawing.** Turning a pack on reloads everything as the level starts to be drawn, and
  the mod's `allChanged` hook discards every region after the frame was prepared from them (a crash on a closed vertex
  buffer). Closing a region's buffers now discards what was prepared; that frame is drawn without the GPU foliage.

### Step 5b research: a swaying copy of the pack's program

- **Building the copy is as on 26.2.** `IrisRenderingPipeline.createShader`/`createShadowShader` keep their signatures;
  `TransformPatcher.patchVanilla`, where the mod splices the sway in (ShaderCreatorMixin), gained a last parameter,
  `Set<String> textureOverrides`. The translated vertex shader still declares `in vec3 iris_Position` and reads
  `iris_transforms.ModelOffset` and `iris_globalInfo` (now in 26.3's member order, which Iris declares itself).
- **Putting it in place of the pack's.** Iris builds the replacement pipeline inside the pass, from the pipeline the
  game compiled: `new FrontendRenderPipeline(name, new GlRenderPipeline(device, createInfo, program, vertexArray), ...)`
  with the attributes tied by name to the program. The same can be done for the mod's copy, from Iris's own result
  for the mod's pipeline (step 5a), changing only the program; `GlRenderPipeline`'s constructor is package-private and
  needs an access widener entry. Built once per program, closed with it.
- **Giving it the sway's blocks.** An Iris program's uniform slots come from a fixed table by name; any other name
  gets none (`MixinGlProgram`), and the GL backend skips a slot with none. The GL backend draws at once
  (`GlRenderPass.drawIndexed` -> `GlCommandEncoder.executeDraw` -> `setupDraw`), binding each slot's buffer to its
  block's point, Iris's at 0 to 6. So the copy's two blocks can be tied to points of their own (7 and 8) with
  `glUniformBlockBinding` when it is built, and the buffers bound there with `glBindBufferRange` just before the
  foliage is drawn -- as the mod's 1.21.1 path already binds its pushes. Iris draws only on OpenGL.

**Step 5b (done):** with a pack loaded the foliage sways, drawn with the mod's own copy of the pack's terrain cutout
program (IrisFoliageShaders: built as on 26.2, ShaderCreatorMixin passing `textureOverrides` on). `withFoliageProgram`
takes Iris's pipeline for the mod's and builds one like it around the copy -- same `CreateInfo`, attributes tied by name,
a `VertexArray` of its own -- once per Iris pipeline. They all share the one program, so closing them would delete it
once for each: only their vertex arrays are closed, and the program once. The sway's blocks are not tied to fixed
points: the copy takes the last two the driver has (`GL_MAX_UNIFORM_BUFFER_BINDINGS - 1` and `- 2`). Nothing hands out
free binding points in GL, and vanilla and Iris count from the first, so the top of the range is the one least likely
to be touched by anyone else. They are bound with `glBindBufferBase` just before the foliage is drawn. Not yet: the
shadow pass (5c).

### Step 5c research: the foliage in the pack's shadow map

(Binding the sway's blocks, first planned as its own step, went into 5b.)

- **When.** Iris draws its shadow map from `LevelRenderer.render`, just before `addMainPass`
  (`MixinLevelRenderer.iris$renderTerrainShadows`): after LevelPassMixin's HEAD hook, before vanilla's main pass
  opens. `ShadowRenderer.renderShadows` draws the terrain in a pass of its own and closes it, then runs the callbacks
  `registerShadowRenderCallback` registers (still in the API, unchanged: sun's model view, projection, camera) with the
  phase set to `TERRAIN_CUTOUT` and **no pass open**. So the mod can write its buffers there and open its own pass, on
  the main target as Iris does for its own.
- **Which program.** `assignPipelineShadow(pipeline, IrisShadowProgram.SHADOW_TERRAIN_CUTOUT)` puts a pipeline in the
  shadow table, apart from the main one, so the same pipeline can be in both; while shadows are drawn
  `getCompiledPipeline` hands back the pack's shadow program in it, and `withFoliageProgram` swaps in the mod's shadow
  copy (already built, from `createShadowShader`, with the same block bindings) instead of the main one.
- **State Iris sets for every pipeline in the shadow pass**: the depth comparison turned round
  (`MixinGlRenderPipeline.bind`), culling off, the viewport and scissor at the map's resolution, and no framebuffer
  bound by the pass (`MixinGlCommandEncoder`) -- the shadow program binds the map's own as it is set up. Unlike 26.2 no
  second, pre-turned pipeline is needed.
- **Uniforms.** The pass is the mod's, so it binds what vanilla binds as it opens the main one
  (`RenderSystem.bindDefaultUniforms`). Iris sets the projection to the sun's (`IrisRenderSystem.setShadowProjection`)
  before the callbacks, but the mod binds the one it is handed, as on 26.2. The fog vanilla sets only inside the main
  pass; the shadow draw binds the frame's terrain fog, which `LevelRenderer.render` is handed and LevelPassMixin sees.
  Each region's transform is written with the sun's model view; the shared index buffer may grow there, no pass being
  open.
- **Drawn apart from the screen's draw**: the shadow draw collects every region (no frustum), so it must not touch
  what was prepared for vanilla's pass (`pendingDraw`), which holds copies of its own.

**Step 5c (done):** plants cast shadows that sway with them. The pack pipeline is also handed to Iris for its shadow
pass (`assignPipelineShadow(..., SHADOW_TERRAIN_CUTOUT)`), where `withFoliageProgram` puts the mod's shadow copy in
place of the pack's shadow program; the shadow callback is registered again, and `drawIntoShadowMap` draws every
region near the player in a pass of its own, with the sun's view and projection, the frame's terrain fog (kept by
LevelPassMixin) and the pushes already written for the screen -- writing them again would step the springs twice.

## Where the renderer hooked in, the first time

- `TerrainPassMixin` prepares the frame at `LevelRenderer.render` HEAD -- before anything is drawn. Buffer
  writes, pipeline compiles and chunk rebuild requests all belong there.
- The same mixin hands the foliage into the pass once the opaque terrain is in, at the `renderGroup` call
  inside `executeSolid`.
- Preparing is not only writing buffers: where foliage is handed over or taken back it asks the chunk mesher to
  build sections again, which reaches into Sodium. Doing that from inside the frame graph took the client down
  natively, with no crash report. See the commit "Prepare the foliage before the world is drawn, not inside it".

## Iris 1.11.6 on 26.3

The mod does not draw through a shader pack on 26.3 yet. This is what an attempt found, and where it stopped.

- **Program substitution.** `MixinShaderManager_Overrides` injects at `RenderSystem.getCompiledPipelineNullable`
  RETURN. For a pipeline `IrisPipelines` knows, it rebuilds the compiled pipeline around its own `GlProgram`:
  takes the old `GlRenderPipeline`'s `CreateInfo` (through Iris's public `GlRenderPipelineAccess`), ties every
  vertex attribute by `glGetAttribLocation` of `iris_<name>` and then `<name>`, builds a `VertexArray`, and
  wraps it all in a new `FrontendRenderPipeline`. A pipeline it does not know is logged as
  `Missing program ... in override list` and left alone.
- **Uniforms are bound by slot.** `FrontendRenderPass.setUniform` turns a name into an index through
  `uniformIndices`, and the index is a slot of **the program**. A program swapped in under a pipeline needs the
  index map of the list it was itself set up with, not the pipeline's own. Until 26.2 the binding was by name
  and the order did not matter.
- **Clouds.** `ExtendedShader` adds `BindGroupLayouts.CLOUD_INFO` to every program it builds, whether or not its
  shaders read the clouds. From 26.3 every uniform a pipeline declares has to be bound before a draw, or
  `GlCommandEncoder.setupDraw` dies on a null buffer view.
- **Reversed depth.** A pack undoes Minecraft's reversed depth in its own shaders (`iris_undoRevZ`), and Iris
  makes up for it in `UndoReverseZThree`, which patches `GlConst.toGl(CompareOp)` -- but only while
  `ImmediateState.isRenderingLevel`, and `MixinGameRenderer` sets that for the length of `GameRenderer.extract`
  alone. The comparison is settled in the `GlRenderPipeline` constructor, so a pipeline built anywhere else
  keeps vanilla's and fails every depth test.
- **Targets.** `MixinGlCommandEncoder` keeps the pack's framebuffer bound for a draw whose program is an
  `ExtendedShader`, and sends anything else back to vanilla's target.

### Where the attempt stopped

With all of the above in place the foliage was still not seen, and tracing showed everything in order: the
program is built with the sway in it (the patched source was dumped and read), the attributes tie
(`Position` → 0 … `SwayCell` → 9), the uniforms match, the mesh is Iris's terrain format (stride 60 = 60), two
regions and three draws are issued, the phase is set to `TERRAIN_CUTOUT`, and nothing is logged.

**The next experiment is to draw with no depth test at all.** If plants appear, the cause is depth; if they do
not, the draw is not reaching the target that is shown, and the thing to read then is how Sodium's chunk draws
land in Iris's targets -- Sodium is in the same position as the mod and works.

## Testing on 26.3

`runClient` used to die at random about a second after the window opened, during the first resource reload: exit
`-1073741819` (`0xC0000005`), no crash report, no `hs_err`, nothing in the Windows event log -- with or without Sodium,
on OpenGL and on Vulkan, and never in the launcher. It was blamed on Sodium's NVIDIA workaround for a while; that was
wrong.

The cause is two JVM arguments 26.3's version manifest adds and Loom does not pass (Loom 1.16.3 hard-codes only
`--sun-misc-unsafe-memory-access=allow` and `--enable-native-access=ALL-UNNAMED`):

- `-XX:StackShadowPages=32`
- `--add-exports java.base/jdk.internal.misc=ALL-UNNAMED`

26.3 compiles every shader with native code (shaderc, then SPIRV-Cross for OpenGL) on its worker threads while the
resources load, and without the extra stack shadow pages that overflows a worker's stack now and then. The client run
in `build.fabric-m.gradle.kts` adds both from 26.3 on. Only development runs are affected: the launcher passes the
manifest's arguments, so the shipped jar never sees this.

When a new version dies natively in development only, diff the manifest's `arguments.jvm` against what Loom passes
first.

## NeoForge 26.3

- **Instance.** NeoForge `26.3.0.26-beta` (every 26.3 build is a beta so far), Sway `26eSF65d`, Sodium 0.9.2 `VHtnT9Q4`
  (compiled against only). No Iris exists for NeoForge 26.3: Stonecutter's `iris` constant and the build's
  `shaderPackSupport` leave the shader pack support out of that one version, and an Iris installed there all the same
  is taken as a pack always loaded, so the chunk mesh keeps the foliage. No Polytone for 26.3 either.
- **Recompiling Minecraft** failed with the NeoForm runtime ModDevGradle 2.0.141 brings (2.0.18): an anonymous
  `HolderSet.Named` narrowing `contents()`. 26.3 uses NeoForm runtime 2.0.31, set for >=26.3 only.
- **JVM arguments.** ModDevGradle passes the manifest's `-XX:StackShadowPages=32` (whose absence killed Fabric's dev
  runs) but not `--add-exports java.base/jdk.internal.misc=ALL-UNNAMED`; the client run adds it on >=26.3.
- **Where to prepare.** `RenderLevelStageEvent.AfterOpaqueBlocks`, which 26.2 prepared and drew from, now fires inside
  vanilla's main pass and hands it over (`LevelRenderer` line ~536): no buffer may be written there. The equivalent of
  Fabric's `LevelExtractionEvents.END_EXTRACTION` is `ExtractLevelRenderStateEvent`, posted as the very last thing in
  `LevelExtractor.extract`, with the `LevelRenderState`. Drawing stays with LevelPassMixin, which is loader-agnostic.
- **Sodium on NeoForge (research).** `sodium-neoforge-0.9.2+mc26.3.jar` carries the mod as a jar-in-jar
  (`META-INF/jarjar/...-mod.jar`). Against the Fabric jar, all 710 classes and shaders they share are byte-identical
  but three of Sodium's own mixins (BakedQuad, ItemModelGenerator, Biome), so everything the renderer names --
  `RenderRegionManager.uploadResults`, `SodiumWorldRenderer`, `RenderSection`, `ChunkBuildOutput`,
  `BuilderTaskOutput`, `LevelSlice`, `ShaderLoader` and the `sodium:blocks/*` shaders -- is the same. Its terrain is
  set up by the shared `LevelExtractorMixin` at `SectionOcclusionGraph.consumeFrustumUpdate` inside
  `LevelExtractor.extract`, before `ExtractLevelRenderStateEvent`, as before Fabric's END_EXTRACTION. It asks a block
  model for its parts through NeoForge's `collectParts(level, pos, state, random, parts)` with its `LevelSlice`
  (`NeoForgeModelAccess.collectPartsOf`), which `NeoforgeFoliageModel` answers. No change is expected to be needed.
